HERMES / FIDUNIO — CURRENT REBUILD SETUP AND RECOVERY GUIDE

PURPOSE
This is the single reusable root-level setup and recovery guide for the current FIDUNIO rebuild. It replaces the obsolete 0.8.1.9 tablet-only setup instructions.

CURRENT DEVELOPMENT BRANCH
- Authoritative in-progress branch: fidunio-complete-rebuild
- Product name: FIDUNIO
- GitHub repository name: hermes
- main contains a curated recovery-document mirror only; do not treat application code on main as the current rebuild until final deliberate promotion.

RELEASE ROADMAP / SCOPE
- First complete rebuild release: core FIDUNIO product functionality, including account/authentication, account-authoritative E2EE, direct/group messaging, attachments, disappearing content, invitations/install, offline behavior, receipts, responsive UI, and final device validation.
- FIDUNIO 1.1: Firebase Cloud Messaging (FCM) notifications. FCM is not required to be active in the first rebuild release and must not block that release.
- FIDUNIO 1.2: Firebase App Check production activation/enforcement. App Check is not required to be active in the first rebuild release and must not block that release.
- Existing App Check client ownership/configuration may remain present with enforcement OFF until the deliberate 1.2 rollout.
- First-rebuild completion percentage and release gate exclude deferred FCM 1.1 and App Check 1.2 work.

MANDATORY START OF EVERY BUILD SESSION
1. Read hermes-memory.txt completely.
2. Read FIDUNIO-BUILD-CHECKLIST.md completely.
3. Read the architecture/security documents required by hermes-memory.txt before consequential code changes.
4. Select work marked NOT DONE or IN PROGRESS in FIDUNIO-BUILD-CHECKLIST.md. Items marked DEFERRED — 1.1 or DEFERRED — 1.2 are roadmap work and do not block the current first-rebuild release.
5. Work only on fidunio-complete-rebuild until the complete candidate passes the repository security/regression gate and is deliberately promoted.
6. After substantive work, update FIDUNIO-BUILD-CHECKLIST.md with the actual state and evidence. Never mark a feature DONE merely because a file or partial implementation exists.

AUTHORITATIVE ARCHITECTURE
- ONE RESOURCE -> ONE OWNER -> ONE PREDEFINED AREA -> ONE SERIALIZED WRITE PATH.
- app.js is the application/UI controller. It coordinates specialized owners and must not own raw cryptography or direct Firebase SDK access.
- firebase.js is the sole Firebase SDK/service owner and transports opaque encrypted records.
- e2ee-account-identity-manager.js owns the durable account E2EE identity lifecycle.
- Direct-message account E2EE uses e2ee:3 through its dedicated runtime/service.
- Group account E2EE uses e2ee:4, group epochs, and dedicated group runtime/service modules.
- Service worker is cache/transport only. Do not put application-semantic repair or encryption transforms in it.
- Firestore is durable authority; local storage is rebuildable cache; encrypted Outbox is authoritative for pending sends.
- Device IDs are not part of account-authoritative message-key derivation or decryptability.

ACCOUNT / RECOVERY RULES
- Local device PIN is 4-12 digits and belongs only to local app security.
- Account E2EE PIN is exactly six digits and belongs to account encryption/recovery. Never conflate the two.
- Recovery requires exactly: verified Firebase account/UID + exact six-digit E2EE PIN + Google-hosted recovery authority.
- Recovery failure must never silently create a replacement E2EE identity.
- App Check enforcement remains OFF for the first rebuild release; deliberate production activation/enforcement is scheduled for FIDUNIO 1.2.
- Firebase/Google console setup for the recovery architecture is complete; do not repeat it unless a later verified requirement explicitly demands a change.

PROTECTED FILES / REPOSITORY RULES
- Never overwrite, regenerate, or package firebase-config.js or config-firestore.js from the Hermes repository workflow.
- version.js is the authoritative visible application version source.
- Keep exactly one cumulative root hermes-memory.txt and one reusable root hermes-setup.txt. Do not create version-numbered memory/setup files.
- Preserve the mandatory iPad/tablet/desktop two-pane layout.
- Preserve iPhone single-pane behavior, prominent Back control, and wrap-around fixes.
- Do not restore MutationObserver-based structural self-repair or competing lifecycle/Firebase owners.

CURRENT PRODUCT STATUS
Use FIDUNIO-BUILD-CHECKLIST.md as the authoritative completion ledger. At this guide's reconciliation, the first complete rebuild estimate remains approximately 65%. Core account/authentication, account-authoritative E2EE, direct messaging, encrypted Outbox, group encrypted messaging, Settings lifecycle, and responsive foundations are substantially integrated. FCM is tracked for 1.1 and App Check enforcement for 1.2, outside the first-rebuild completion gate.

GROUP REQUIREMENTS
- Group messages use e2ee:4 and the fidunio-group-message-v1 format.
- Membership changes rotate keyEpoch before subsequent messages.
- New members receive only the new epoch by default; historyPolicy is fromJoin. Explicit earlier-history sharing uses an admin-selected starting point/date (including Beginning of conversation) and must be message-granular so no content before the chosen boundary becomes decryptable.
- Removed members receive no new epoch envelope.
- Group receipts are per-account UID.
- Group Outbox retry must revalidate the current epoch and re-encrypt when required.

DISAPPEARING CONTENT
- Disappearing messages and attachments are part of the first rebuild release.
- On expiry, all application-controlled traces must be physically purged, including Firestore message documents, receipts/references, ciphertext, attachment metadata/chunks/blobs, thumbnails/previews, local history/cache, decrypted object URLs, Outbox copies, and any application-owned notification records.
- No soft-delete, expired marker, or per-message tombstone may remain.
- Offline/stale clients must not resurrect expired content.

FCM — FIDUNIO 1.1
- FCM is deferred to version 1.1 and is not required to be active for the first rebuild release.
- When implemented, FCM is notification/wake transport only; Firestore remains message authority.
- Push payloads must not expose plaintext message/attachment content by default.
- Multiple notification endpoints may be associated with one UID.
- Fire OS/non-FCM clients must remain fully usable through Firestore synchronization when opened.

APP CHECK — FIDUNIO 1.2
- App Check production enforcement is deferred to version 1.2 and is not required to be active for the first rebuild release or 1.1 unless deliberately changed.
- Existing centralized App Check client ownership in firebase.js may remain with enforcement OFF.
- Before 1.2 enforcement, validate all legitimate supported browser/PWA/device/recovery flows and prove no legitimate-client lockout.

INVITATION / INSTALL LANDMINE
A previous automatic invite/install/icon integration broke Settings and the two-pane UI. Do not adapt or restore that implementation. Invitation behavior and install-to-Home-Screen integration must be rebuilt under deterministic owners and integrated only after their logic is independently sound.

HTEST POLICY
- htest is not continuously synchronized with fidunio-complete-rebuild.
- The current htest deployment may be stale/incomplete and must not be used to judge the current rebuild unless a deliberate candidate deployment has just been performed.
- Do not deploy every intermediate commit to htest.
- After the complete coherent candidate passes the full repository gate, deploy it atomically to htest for the user's final iPhone/iPad/two-device/offline/recovery testing.

FINAL PRODUCT GATE — FIRST REBUILD RELEASE
Before declaring READY FOR TEST:
1. Complete every first-rebuild item in FIDUNIO-BUILD-CHECKLIST.md. Deferred 1.1 FCM and 1.2 App Check items do not block this gate.
2. Remove simulations and unsupported placeholder controls or replace them with real supported behavior.
3. Run the complete repository security/regression gate on the exact first-rebuild candidate commit.
4. Reconcile hermes-memory.txt, this hermes-setup.txt, and FIDUNIO-BUILD-CHECKLIST.md.
5. Deliberately deploy the exact complete candidate to htest.
6. Verify the htest Pages deployment corresponds to that candidate.
7. Only then ask the user to perform final device testing.

RECOVERY FROM A NEW CHAT OR INTERRUPTION
Start with CURRENT-REBUILD.md on main if necessary. Then read the mirrored hermes-memory.txt and FIDUNIO-BUILD-CHECKLIST.md to locate the active branch and current state. Return to fidunio-complete-rebuild for executable development. The curated main-branch documents are recovery/discovery copies, not evidence that unfinished application code has been promoted.
