FIDUNIO / HERMES ARCHITECTURE OWNERSHIP RULES
Reference baseline: validated 0.9.4.11

PURPOSE
This document records the architecture rules adopted after repeated Settings and PIN/lifecycle race failures. It is a permanent reference for future changes.

CORE RULE
ONE RESOURCE -> ONE OWNER -> ONE PREDEFINED AREA -> ONE SERIALIZED WRITE PATH

UI OWNERSHIP
1. Every functional screen/section has one structural owner.
2. A feature may mutate only the DOM container explicitly assigned to it.
3. A feature must not discover and write to a shared parent such as .content.settings, #app, or document.body for ordinary screen content.
4. Parent controllers may create section containers and show/hide/select them, but must not rewrite another section's contents.
5. No feature may re-parent or replace DOM nodes owned by another feature.
6. Orientation/resize may change geometry only. It must never be required to make a feature appear or function.

ASYNC / MUTEX RULE
1. Shared mutable resources use one owner.
2. Async writes by that owner are serialized through a local mutex/queue.
3. Do not use loose global busy flags that drop work with `if (busy) return`.
4. Isolation prevents cross-owner interference; mutexes prevent an owner's own async races.
5. Prefer automatic release via try/finally.

SETTINGS FINDING (0.9.4.11)
The validated 0.9.4.11 Settings page is rebuilt by app.js using `app.innerHTML` inside renderSettings(). This destroys the previous Settings DOM every time renderSettings() runs.

The three late-added sections are different from the original Settings cards:
- Profile is created later by auth-ui.js.
- Invitations is created later by auth-ui.js and further enhanced by invite-modal.js.
- User Administration is created later by admin-ui.js.

In 0.9.4.11 these modules survive the destructive render only because broad MutationObservers watch the document and recreate/re-append their cards after app.js rewrites Settings. settings-polish.js then observes those mutations and moves/re-parents the cards into its panels.

Therefore the old working behavior is a self-repair loop, not true ownership:

app.js renderSettings()
  -> replaces entire Settings DOM
  -> auth-ui/admin-ui observers notice mutation
  -> Profile / Invitations / User Admin are appended again
  -> settings-polish observer notices mutation
  -> cards are moved into Settings panels again
  -> invite-modal observer notices Invitation card and modifies it

This explains why removing the observers in the first isolation attempt made exactly Profile, User Administration and Invitations disappear. They were never part of the authoritative Settings render lifecycle.

CORRECT SETTINGS DIRECTION
The next Settings implementation must preserve the successful lifecycle while eliminating observer-based self-repair.

Required model:
1. app.js remains the authoritative route/screen renderer.
2. renderSettings() creates permanent, predetermined hosts for all Settings sections as part of the authoritative render.
3. After the hosts exist, one deterministic Settings controller mounts each feature owner into its assigned host.
4. Profile receives only the Profile host.
5. User Administration receives only the Users host.
6. Invitations receives only the Invitations host.
7. Feature modules never receive .content.settings and never append to it.
8. settings-polish must not re-parent feature cards after creation.
9. No whole-document MutationObserver is used to restore Settings features after app.js redraws the screen.
10. Any later renderSettings() call recreates the fixed hosts and then deterministically invokes the same feature-mount sequence.

IMPORTANT DISTINCTION
The repeated failure was initially described as a rogue writer erasing late Settings panels. Investigation shows the primary destructive writer is the legitimate app.js renderSettings() function itself. The real defect is that the three late features were outside the authoritative render lifecycle, so observer code had been compensating for that omission.

PIN / BIOMETRIC FOLLOW-UP
The local security design already keeps app.js state.unlocked as the authoritative lock state, which is good. However some local-security configuration operations update a shared cached configuration and launch IndexedDB writes independently. These should later be reviewed for read/modify/write races and serialized under one local-security owner. This work follows Settings stability and the Fire HD 8 account-isolation issue.

BROADER AUDIT TARGETS
Review all modules for:
- document-wide or #app-wide MutationObservers used as lifecycle control
- features that search for another module's parent container and append into it
- modules that call innerHTML on a shared parent they do not exclusively own
- multiple writers to the same IndexedDB key/object
- async read/modify/write sequences without serialization
- independent Firebase initialization or duplicated session ownership
- location.reload() used by low-level services
- global flags used as concurrency control
- route/layout code that changes functionality based on orientation timing

KNOWN PROTOTYPE-ERA OBSERVER RISKS IN 0.9.4.11
- auth-ui.js: document-wide observer used to mount Profile/Invitations.
- admin-ui.js: document-wide observer used to mount User Administration.
- settings-polish.js: #app subtree observer used to rearrange Settings.
- invite-modal.js: document-wide observer used to enhance Invitations.
- main-screen-polish.js: document-wide observer used to polish main UI.
- bootstrap.js: document-wide observer used to scrub prototype UI.
- new-message-polish.js: #app subtree observer used to install recipient UI.

These are audit targets; their presence alone does not prove a current bug.

VALIDATION DISCIPLINE
- Start changes from a user-validated checkpoint.
- Change one ownership boundary at a time.
- Preserve established visual design unless the user requests a UI change.
- Give each test build a distinct visible version.
- Test direct load in target orientation; never use rotation as a recovery step.
- Test leaving/re-entering the screen and repeated asynchronous updates.
- If a build fails, roll main back to the validated checkpoint before the next attempt.

- Read-side owner: e2ee-account-group-conversation.js.

GROUP HISTORY SOURCE AUTHORITY — 0.9.6.9

- The controller/integration boundary carries only target/boundary intent.
- Runtime owns secure grant ID generation and boundary/source selection before message-granular re-encryption.

DISAPPEARING FIRST-READ AUTHORITY — 0.9.6.10
- Policy resource owner: `disappearing-content-policy.js` decides expiry/purge eligibility only.
- Persistence/write owner: `firebase.js` serializes direct and group receipt transitions and is the only SDK owner writing server-backed `readAt`.
- Firestore Rules enforce recipient/account ownership and immutable first-Read timestamps.
- app.js and the group conversation owner may request Delivered/Read transitions but do not choose or persist authoritative timestamps.
- Future physical purge is a separate mutable resource and must have one dedicated serialized deletion owner; do not scatter deletes among UI/subscription modules.

DISAPPEARING OUTER MESSAGE METADATA — 0.9.6.12
- Resource: resolved per-message disappearing duration.
- Policy owner: `disappearing-content-policy.js`.
- Pending-send authority: encrypted Outbox preserves the resolved duration; reconnect must not recompute it from a changed user preference.
- Cloud write owner: `firebase.js`; current direct/group ciphertext rows may carry optional `disappearAfterSeconds`.
- Crypto owners remain unchanged and must not absorb disappearing metadata into their exact envelopes.
- Firestore Rules bound and freeze the metadata.
- Physical purge is a different resource and still requires one dedicated serialized deletion owner.

DISAPPEARING PURGE DECISION AUTHORITY — 0.9.6.13
- `disappearing-purge-policy.js` is the pure eligibility owner. It decides whether a source is eligible for final purge but performs no deletion and imports no Firebase/Admin/local-storage/UI owner.
- Production purge evaluation must supply server-side time; device clocks cannot authorize cloud deletion.
- Direct source eligibility is recipient first-Read + immutable duration elapsed.
- Group source eligibility uses the source epoch recipient set, excluding sender, intersected with current entitlement. New members outside that epoch are not retroactive recipients; removed members no longer block source deletion.
- Physical deletion is a separate mutable resource. It still requires one dedicated serialized server purge owner using bounded repository APIs; do not scatter deletes through app.js, subscription callbacks or group crypto modules.

DISAPPEARING PURGE EXECUTOR AUTHORITY — 0.9.6.14
- Resource: final disappearing-source purge coordination, separate from pure eligibility and separate from physical Firestore/Storage mutation.
- Pure decision owner: `disappearing-purge-policy.js`.
- Serialized coordination owner: `disappearing-purge-executor.js`.
- Future mutable delete owner: one dedicated server repository/adapter only; no app.js/firebase.js/browser delete path and no client delete rules.
- Read/evaluate cycle requires authoritative server time and an opaque repository basis. Commit must re-read/revalidate that basis with transaction/precondition semantics; stale basis fails closed.
- The executor's local queue serializes one process only. Cross-instance/cloud correctness must come from the repository's transaction/precondition path.
- Physical trace deletion, scheduler, local cache/Outbox convergence and attachments remain separate unfinished resources.

DISAPPEARING FIRESTORE PURGE REPOSITORY — 0.9.6.15
- `disappearing-purge-firestore-admin-adapter.mjs`: server-only physical Firestore repository boundary; receives Admin Firestore by injection and does not initialize/import a competing Firebase SDK owner.
- Direct read/commit owns only authoritative server state + transactional source deletion under opaque update-time basis revalidation.
- Group read owns only authoritative source/group/epoch/receipt state acquisition. Group physical delete remains fail-closed until subordinate receipt/history-grant trace cleanup is complete.
- Eligibility remains exclusively in `disappearing-purge-policy.js`; orchestration remains exclusively in `disappearing-purge-executor.js`.

DISAPPEARING GROUP GRANT TRACE PLANNER — 0.9.6.16
- `disappearing-group-grant-trace-plan.js`: pure subordinate history-grant reconciliation owner only.
- Inputs: complete grant metadata/copy rows for one group plus disappearing `sourceMessageId`.
- Outputs: copies to delete, grants to delete, and grants to update with recomputed count/earliest retained source.
- It owns no Firebase/Admin SDK, Firestore write, crypto, UI, cache, timer or scheduler.
- `disappearing-purge-firestore-admin-adapter.mjs` remains server read/write repository owner and now includes grant/copy update times in group purge basis.
- Group physical commit remains fail-closed until concurrent grant creation changes a basis-visible authority and all receipt/grant/source writes can be revalidated together.

GROUP HISTORY-GRANT PURGE BARRIER — 0.9.6.17
- New history-grant creation remains owned by `firebase.js` browser Firestore transport.
- Resource coupling required for purge safety: a genuinely new grant atomically touches only group `updatedAt` plus the new grant document.
- Firestore Rules enforce the same-request barrier; callers cannot create a grant without a basis-visible group authority change.
- Group purge repository continues to own server read/delete authority and includes group update-time in its opaque basis.
- No second purge/grant owner is introduced.

GROUP HISTORY-COPY PURGE BARRIER — 0.9.6.18

- A non-empty new-copy chunk and parent group `updatedAt` are one batch and one server timestamp authority.

- Existing-copy idempotent retry writes nothing and does not manufacture a barrier update.
- Server group purge repository remains the sole physical-delete owner; no delete capability moved to the browser.
