E2EE CRYPTO + FIRESTORE SPECIFICATION — SEPTEMBER 5, 2026
- Frozen v1 direction: ONE ACCOUNT = ONE durable random account E2EE identity.
- Browser-native Web Crypto direction: ECDH P-256 account key pair, versioned.
- Normal private-key protection: AES-256-GCM.
- Password+PIN KDF: PBKDF2-HMAC-SHA-256, v1 600,000 iterations, random unique salt, random unique GCM IV.
- Password + exactly six-digit FIDUNIO PIN required together. Encode inputs unambiguously; never naive ambiguous concatenation.
- Firestore target private identity path: `users/{uid}/e2ee/identity`, with schemaVersion, identityVersion, stable random keyId, algorithm, public material, versioned normalWrapper, versioned recoveryWrapper metadata, state, monotonic revision, timestamps.
- Firestore never contains plaintext password, PIN, private E2EE key, derived normal wrapping key, recovery master secret or Secret Manager material.
- Separate public-key publication path/rules from private wrapper so correspondents never receive access to private identity document.
- Wrapper should cryptographically bind account/version context (uid/keyId/schema/wrapper versions where practical); exact canonical serialization/AAD must be fixed and tested before production writes.
- Exactly one Account E2EE Identity Manager owns create/unlock/recovery/re-wrap; duplicate startup/auth callbacks join same serialized operation.
- Identity creation is create-once. Missing local state never authorizes replacement. If create race is lost, discard candidate and use authoritative identity.
- Password/PIN change re-wraps SAME private key. Candidate wrapper generated and locally verified first, then Firestore compare-and-update transaction checks expected keyId/revision and atomically writes wrapper + incremented revision.
- Firestore transaction callbacks may retry, so they MUST NOT generate identities or mutate UI/application state as side effects. Generate crypto candidate outside transaction; transaction only validates/commits prepared data.
- Firebase Auth password update and Firestore wrapper update are not assumed cross-service atomic. Use explicit recoverable staged flow. Never destroy last valid wrapper before replacement is verified/authoritative. Failure enters deterministic retry/recovery, never silent new identity.
- Recovery rollback invariant: NEVER remove last usable recovery path before replacement is proven valid; NEVER respond to failed re-wrap/recovery by generating new identity.
- Client private-wrapper access only for owning authenticated UID. Recovery-only transitions server-only. Public key separate.
- Cloud Functions/Admin SDK bypass ordinary Firestore client Rules, therefore recovery service account IAM must be least privilege. Secret Manager access only to required recovery function. App Check may be additional abuse defense, never replacement for Auth/Rules/crypto.
- Binding detailed reference: `ACCOUNT-E2EE-FIRESTORE-AUTHORITY.md`.

ACCOUNT E2EE RECOVERY DECISIONS — SEPTEMBER 5, 2026
- PASSWORD + EXISTING SIX-DIGIT FIDUNIO PIN together for normal durable unlock/recovery on new/reinstalled context; neither alone sufficient.
- Firebase Authentication owns auth password; FIDUNIO never persists plaintext password/PIN.
- Password/PIN changes preserve SAME E2EE identity/history through re-wrap.
- Forgotten-password product requirement: legitimately recovered account regains SAME E2EE identity and historical messages.
- Simple recovery UX: verify registered email/recovery channel -> existing six-digit PIN -> additional approved recovery verification -> server recovery authorization -> same private key -> new password -> new normal wrapper -> history restored.
- No mandatory second device, QR transfer, proprietary device ID or recovery-code requirement for normal recovery.
- Security questions supplemental only, never sole proof or cryptographic recovery secret.
- Recovery hardened: short-lived/single-use challenge/session, strict throttling/rate limits, enumeration resistance, notification after success, deterministic session review/invalidation and failure states.

SERVER-SIDE RECOVERY AUTHORITY — AGREED
- Small narrowly scoped Firebase/Google serverless recovery component; intended Cloud Functions + Google Secret Manager or equivalently reviewed Google-managed secret facility.
- Not a general FIDUNIO message server. Normal messaging remains client E2EE/Firestore ciphertext.
- Recovery capability never in browser JS, Firestore, GitHub or logs.
- Function does not store message plaintext, Firebase password or plaintext PIN and no administrator plaintext-key bypass.
- Accepted tradeoff: recovery authority is part of security boundary because user requires history recovery without second-device/recovery-code dependency.

OFFLINE MESSAGING — AGREED
- FIRESTORE = durable authoritative/master encrypted conversation/message record.
- LOCAL CACHE = rebuildable offline/readable working copy.
- OUTBOX = one temporary owned local queue for encrypted pending sends.
- Offline read uses cache. Offline send shows Pending/Waiting, never falsely Sent.
- Reconnect automatically sends queued work, receives missed authoritative changes, reconciles cache, resumes live sync.
- Stable/idempotent message IDs + one serialized Outbox path prevent duplicate authoritative messages.
- Missing local DB = cache miss, not lost history. UID-isolated cache prevents account leakage.
- Firestore SDK persistence may assist but cannot become competing Outbox/state owner.
- Firestore transactions are not relied on offline; explicit FIDUNIO Outbox owns offline retry.
