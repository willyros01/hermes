E2EE FOUNDATION — 0.7.0 / 0.7.1
- Per-installation non-exportable ECDH P-256 private key stored locally in IndexedDB.
- Public JWK is published to the signed-in user's Firestore profile.
- ECDH shared secret -> HKDF-SHA-256 -> AES-256-GCM.
- Fresh 12-byte IV for each message.
- Conversation ID used as AES-GCM additional authenticated data.
- New encrypted direct messages store e2ee=1, ciphertext, iv, and text="" in Firestore.
- Recipient decrypts locally.
- 0.7.1 keeps this E2EE design; it fixes version consistency rather than changing cryptography/rules.

0.7.2 REPAIR
- First 0.7.1 E2EE test: iPad outgoing `Encrypted 0.7.1 from iPad` immediately showed Failed; iPhone no longer displayed the existing iPad cloud conversation.
- Root defect in local merge: `firebase.js` conversation discovery supplied `peerUid`, but `app.js` `mergeCloudConversation()` did not retain it. E2EE send needs peerUid to fetch the peer public JWK.
- 0.7.2 preserves peerUid in cloud-conversation merges and encrypted Outbox conversation recovery data.
- Added authoritative repair path: if a local cloud conversation has no peerUid, read the Firestore conversation document, verify current account membership, derive the other member UID, merge/persist the repaired identity, then fetch the peer public key.
- Conversation discovery now reattaches the active cloud message subscription and retries durable Outbox work after identity repair.
- Do not ask user to recreate accounts, create a replacement conversation, or copy/paste FIDUNIO IDs again for this repair.
- Firestore rules are unchanged in substance from 0.7.0/0.7.1; user should leave already-published E2EE rules in place.
- version.js remains the single authoritative version file; current release 0.7.2.


0.7.3 — LIVE RECEIVE / RECONNECT RELIABILITY
- 0.7.2 direct E2EE passed both directions on iPad/iPhone.
- Existing conversation restoration after iPhone authentication passed.
- A previously failed iPad message automatically retried and arrived after the iPhone signed in and its E2EE key was available.
- Offline encrypted Outbox survived repeated close/reopen while offline.
- After communications returned, the queued message eventually sent and arrived readable, but delivery was slow and the iPhone needed to leave/re-enter the conversation to display it.
- 0.7.3 addresses that reliability issue without changing cryptography or Firestore rules.
- Root cause/race addressed: conversation discovery snapshots can update when a message touches conversation.updatedAt. Earlier code re-ran ensureActiveCloudMessageSubscription(), which always stopped/restarted the active message listener. 0.7.3 makes same-conversation subscription idempotent.
- Explicit navigation/auth/reconnect/foreground events may force one clean reattach.
- Reconnect Outbox recovery now flushes immediately, then retries after 1.5s and 4s because iOS can report online before Firebase requests are actually ready.
- Test 0.7.3 for prompt automatic queued-send after reconnect and live display on the already-open receiving conversation without navigating out/in.


0.8.0 — DEVICE IDENTITY / MULTI-DEVICE FOUNDATION
- Built from the stable 0.7.3 direct-E2EE + offline/reconnect baseline.
- 0.7.3 passed instant two-way live receipt and queued reconnect delivery without leaving/re-entering the conversation.
- Preserve the 0.7.3 listener/reconnect/local-first/Outbox architecture as rollback/reference baseline.
- 0.8.0 gives every installation a stable random local Device ID.
- It REUSES the existing 0.7.x non-exportable ECDH P-256 keypair rather than rotating the working key during upgrade.
- It computes a SHA-256 public-key fingerprint and displays it under Settings → Device Identity.
- It publishes public device records at users/{uid}/devices/{deviceId}.
- New encrypted message rows carry senderDeviceId metadata.
- The account-level e2eePublicJwk remains the active compatibility encryption key in 0.8.0 so existing direct E2EE behavior is preserved.
- Full recipient per-device ciphertext/envelope fan-out is NOT implemented yet; 0.8.0 is only the identity/registry foundation.
- Firestore rules now include explicit device-subcollection access: authenticated read of public device records, owner-only create/update, no delete.
- 0.8.0 therefore DOES require publishing the included Firestore rules before device-registry testing.
- Protected firebase-config.js and config-firestore.js remain excluded.
- Required regression: instant two-way existing conversation, offline queued survival, reconnect automatic send/live receipt.


0.8.1 — CONTACT KEY VERIFICATION / KEY-CHANGE DETECTION
- Built from 0.8.0 after 0.8.0 passed device registration on iPad/iPhone, instant two-way encrypted messaging, offline queued persistence, and reconnect delivery.
- 0.8.1 preserves 0.7.3 transport/local-first/Outbox/reconnect architecture and 0.8.0 device registry.
- Adds encrypted local peerTrust records keyed by peer UID.
- First observed peer account public-key fingerprint is recorded.
- Conversation Info for cloud direct chats becomes Conversation Security.
- Shows current peer fingerprint and registered-device count.
- User may explicitly Verify Current Key only after comparing fingerprints through a separate trusted channel.
- Verified-key change causes a visible security warning and blocks NEW sends until the new current key is explicitly verified.
- Unverified key changes are warned but not treated as previously trusted.
- Peer public keys are refreshed during live snapshots and before sends to detect changes instead of relying forever on peerKeyCache.
- 0.8.1 verification is local per installation; no QR linking or automatic cross-device verification yet.
- Firestore rules unchanged from 0.8.0.
- Protected firebase-config.js and config-firestore.js remain excluded.
- Do not deliberately clear site data to test key-change detection on the main test accounts; use a disposable controlled scenario later if needed.
