DETERMINISTIC UI REQUIREMENT — SEPTEMBER 5, 2026
- User's explicit one-word requirement: DETERMINISTIC.
- All actions' results should be as expected. UI correctness must not depend on timing races, orientation changes, cache warming, repeated observers, asynchronous collision, or one module repairing another module after the fact.
- Major concern: the current UI has too many moving parts that can crash against each other, including app.js rendering/navigation, feature modules, auth callbacks, Settings lifecycle code, Firestore live events, receipt/message updates, service-worker-injected behavior, responsive/two-pane transitions, and historical DOM repair/re-parenting logic.
- A screen looking correct is NOT equivalent to the UI architecture being complete. Multiple independent writers can still make the UI nondeterministic.
- The goal is NOT increasingly masterful synchronization of many writers. The goal is to eliminate unnecessary writers and competing authorities.
- Authoritative application state comes first; the DOM is a projection of that state.
- Firestore, E2EE, receipts, auth, local-cache synchronization, and orientation changes should update state or dispatch owned events. They should not independently manipulate arbitrary screen DOM.
- Every major UI region/screen must have one structural owner and one predefined DOM area. Sibling modules must not move/remove/recreate each other's nodes.
- Messages owner renders Messages. Settings owner renders Settings. New Message owner renders New Message. Layout owner projects one-pane/two-pane. Auth changes account/auth state rather than rebuilding unrelated screen DOM.
- Broad MutationObserver repair, timeout settling, orientation rescue, cache-timing rescue, repeated DOM rediscovery/re-parenting, and location.reload synchronization are prohibited as normal architecture.
- Responsive behavior must be a deterministic projection of the same state, not a second application lifecycle. iPhone single-pane and iPad two-pane remain protected user-facing behavior.
- The 0.9.5.1 Settings lifecycle repair is the precedent for the whole app: owned hosts, explicit lifecycle, no observer-based resurrection.
- UI completion was previously overestimated based on visible/functionality completion. Current architectural confidence is closer to ~60-65%, while roughly 85-90% of the visual/user-facing UI design/functionality may still be reusable. Do not wholesale redesign approved screens; consolidate ownership/lifecycle underneath them.
- Binding reference: `DETERMINISTIC-UI-LIFECYCLE.md`.

MAJOR ARCHITECTURE CORRECTION — SEPTEMBER 5, 2026
- The former rule `one account + one browser installation = one E2EE device identity` is SUPERSEDED.
- User identified the major durability gap: Safari and Home Screen PWA have separate local storage, and local browser storage is not durable enough to be authoritative for conversation continuity or the only copy of cryptographic identity needed to read Firestore history.
- New binding invariant: ONE ACCOUNT = ONE DURABLE E2EE IDENTITY.
- Firebase Auth UID is the durable FIDUNIO user identifier. UID identifies the account but is NOT secret and MUST NOT by itself be used to derive the private encryption key.
- Account E2EE secret/key material must be cryptographically random and generated once. Public material may be stored in Firestore. Private material must never be stored in plaintext in Firestore; it must use a reviewed encrypted/wrapped recovery package so a newly authenticated installation can recover the same account identity.
- FIRESTORE IS AUTHORITATIVE for encrypted conversations/messages.
- LOCAL INDEXEDDB/STORAGE IS A REBUILDABLE CACHE for inbox/history performance and offline use. Outbox is a temporary offline queue. Loss of local cache must cause reconstruction, not permanent loss of history.
- PWA removal/reinstall, Safari-vs-PWA context changes, cache deletion, or replacement device must not by themselves destroy access to authoritative conversation history.
- Device ID may still be generated/collected as an informational variable for possible future use, but DO NOT use it for E2EE routing, key ownership, message ownership, conversation history, decryptability, or normal delivery.
- Do not continue the per-device E2EE envelope/fan-out architecture as the target design. Existing code is legacy migration material and must be handled under the runtime-consolidation plan rather than blindly deleted.
- Future push notification routing should associate FCM registration tokens with authenticated UID. A proprietary FIDUNIO device ID is not required merely for FCM delivery.
- Existing local PIN remains an installation-local app-lock feature unless deliberately redesigned. It must not become the sole durable source of the permanent account E2EE identity.
- Current iPhone/iPad messaging/device-ID test is paused. Do not create more baseline messages against the old architecture until durable account-key wrapping/recovery and Firestore-authoritative synchronization are designed/implemented in bounded steps.

SAFARI VS HOME SCREEN PWA FINDING — RETAINED
- iOS/iPadOS Safari and an installed Home Screen PWA can have separate local storage/security contexts even on the same physical device.
- They may therefore have different installation-local PIN/cache/device-variable state.
- Under the NEW architecture this separation must NOT imply separate durable E2EE identities or loss of history. Both contexts, after proper authentication/recovery, must reach the same account E2EE identity and Firestore-authoritative history.

PIN / LOCAL SECURITY
- `app.js state.unlocked` remains the single authoritative local LOCKED/UNLOCKED state.
- `local-security.js` is helper-only and must not create competing lock state/UI.
- PIN config is installation-local in IndexedDB; raw PIN never stored; PBKDF2-SHA256 verifier, random salt, 210000 iterations; 4-12 digits.
- WebAuthn platform authenticator with PIN fallback.
- Firebase authentication and local unlock remain separate.
- Known open bug: Remove Local PIN does not work. Change PIN, Lock Now, timeout and existing PIN flows work. Fix later as focused defect.
