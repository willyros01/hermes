ACCOUNT E2EE IDENTITY MANAGER — ISOLATED IMPLEMENTATION, SEPTEMBER 5, 2026
- New `e2ee-account-identity-manager.js` is the sole proposed owner/state machine for durable account identity lifecycle. Commit `bf471bbc5190cc91d4a6e5446573c1a165afd60c`.
- It is deliberately adapter-driven and NOT connected to production Firebase, Firestore, DOM, local storage, service worker or app.js yet.
- States: EMPTY, ENROLLING, LOCKED, UNLOCKING, READY, REWRAPPING, RECOVERING, ERROR.
- All operations share one serialized promise tail. A manager instance binds to one UID until explicit sign-out reset; cross-account reuse is refused.
- Enrollment checks authoritative store first and refuses replacement if identity already exists; crypto generation happens outside retriable Firestore transaction logic through adapter boundary.
- Enrollment creates normal password+PIN wrapper + recovery RUK wrapper + server-protected RUK metadata, then asks identityStore for one deterministic create operation covering private/public records.
- Unlock uses Password + exact six-digit PIN and retains only runtime CryptoKey/keyId/revision in manager memory.
- Re-wrap verifies old wrapper, creates/verifies candidate new wrapper, then compare-and-updates expected revision while preserving keyId/public/recovery identity.
- Recovery accepts RUK only from the separately authorized recovery flow, decrypts SAME identity, creates/verifies new normal wrapper and compare-and-updates expected revision.
- Sign-out reset drops runtime identity reference and UID binding.
- New isolated `e2ee-account-identity-manager-tests.html/js` uses only in-memory adapters and tests create-once, public-key privacy, recovery PIN handoff, locked reload, wrong PIN, unlock, revision increment, key/public/recovery continuity, old credential failure, new credential success, cross-account refusal and serialized READY state.
- These tests are the next iPad Safari gate before production adapters/rules are wired.
- Existing `firestore.rules`, `firebase-service.js`, app.js, service-worker.js and visible app version remain untouched at this stage.

E2EE V1 EXACT WIRE FORMAT + IMPLEMENTATION PROGRESS — SEPTEMBER 5, 2026
- Exact binding format is now in `E2EE-V1-CRYPTO-FORMAT.md`.
- Account key remains ECDH P-256. Public key serialized as Web Crypto JWK. Private wrapper plaintext serialized as DER PKCS#8 bytes, never plaintext-persisted.
- Firestore binary wrapper fields use base64url WITHOUT padding.
- Exact password+PIN KDF input bytes: UTF8(JSON.stringify(["FIDUNIO-E2EE-KDF",1,password,pin])). Password is not trimmed/case-folded/normalized; PIN exactly six ASCII digits and leading zeroes are significant.
- PBKDF2-HMAC-SHA-256 600000 iterations, random 16-byte salt, derived non-extractable AES-256-GCM key.
- AES-GCM uses random 12-byte IV and 128-bit tag.
- Exact normal AAD bytes: UTF8(JSON.stringify(["FIDUNIO-E2EE-WRAP",1,"normal",uid,keyId,schemaVersion,identityVersion,wrapperVersion])). Recovery uses same ordered array with purpose `recovery`.
- New isolated pure module `e2ee-account-crypto.js` implements v1 primitives and owns NO Firebase/Firestore/DOM/storage/lifecycle.
- `FIRESTORE-E2EE-V1-RULES.md` is staging specification only. Existing `firestore.rules` remains untouched until Rules/Emulator validation.
- Public client v1 key publication is CREATE-ONCE. Ordinary client update/delete denied. Private client update limited to normalWrapper + exact revision increment + updatedAt.

E2EE PUBLIC/PRIVATE + RECOVERY ESCROW DECISIONS
- Private: `users/{uid}/e2ee/identity`, owner client only. Public: `e2eePublicKeys/{uid}`, registered users read.
- ONE ACCOUNT = ONE durable random E2EE identity. Device ID informational only.
- Recovery uses random 256-bit RUK. Client encrypts SAME private key under RUK; recovery authority protects RUK using PIN + server master secret boundary. No plaintext PIN/RUK/private key/master secret in Firestore.
- Recovery authority is explicitly trusted provider-assisted security boundary, not zero-knowledge recovery.
- `E2EE-RECOVERY-PROTOCOL.md` is binding: Firebase password reset, restricted authenticated recovery session, existing six-digit PIN cryptographically gates RUK, 10-minute session, max 5 PIN failures/session, max 10 consecutive account-level failures before hold, App Check, least-privilege IAM, notification and no secret logging.
