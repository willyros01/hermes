E2EE PUBLIC/PRIVATE + RECOVERY ESCROW DECISIONS — SEPTEMBER 5, 2026
- Private identity target: `users/{uid}/e2ee/identity`; authenticated owner only through client access. Never expose private wrapper to correspondents.
- Public correspondent lookup target: `e2eePublicKeys/{uid}` containing only uid, versions, stable keyId, ECDH-P256 algorithm, publicJwk, ACTIVE state, timestamp. Registered authenticated users may read public key records; owner-only controlled publication/update; no normal client delete.
- Existing `firestore.rules` is legacy/current production and contains per-device E2EE permissions. Do NOT wholesale replace it. Add new rules in bounded form and Emulator-test them; preserve invitations/roles/conversations/groups/receipts. Legacy devices rules remain until migration is validated.
- Recovery architecture now uses random per-user 256-bit Recovery Unlock Key (RUK). Client encrypts SAME account private key under RUK with AES-256-GCM. Recovery function protects/wraps RUK using server recovery KEK/capability held through Google Secret Manager/KMS boundary. Firestore stores recovery ciphertext + wrappedRecoveryKey, NEVER plaintext RUK/KEK/private key.
- Normal enrollment does not require sending the account private key to recovery server. Server receives transient RUK for protection, not message plaintext/private identity key.
- Forgotten-password recovery: authorized recovery function unwraps/releases per-user RUK only after approved short-lived recovery authorization; client uses RUK to recover SAME private key, then creates/verifies new Password+6-digit-PIN normal wrapper and commits by expected keyId/revision.
- Recovery authority remains explicitly trusted security boundary because it can authorize release of recovery capability. No claim of zero-knowledge recovery.
- Recovery callable should use Firebase Auth context and App Check as abuse defense where supported; App Check supplements, never replaces recovery authorization.
- Cloud Functions/Admin SDK bypass client Firestore Rules, so server recovery IAM must be least privilege.
- Public/private creation should be one deterministic identity-owner operation; cryptographic generation outside retriable Firestore transaction callbacks.
- AES-GCM authenticated context must bind schema/identity version, UID, keyId, wrapper purpose/version using canonical encoding fixed by tests.
- Required tests include wrong password/PIN, tamper, cross-account wrapper transplant, non-owner private read, public record field leakage, concurrent revision, failed recovery/re-wrap, reinstall/cache loss, offline/reconnect.
- Binding detail: `ACCOUNT-E2EE-FIRESTORE-AUTHORITY.md` commit beginning `04ed758c`.

E2EE CRYPTO SPECIFICATION — FROZEN V1 DIRECTION
- ONE ACCOUNT = ONE durable random account E2EE identity.
- Web Crypto ECDH P-256 account key pair, versioned.
- Normal private-key wrapper AES-256-GCM.
- Password+PIN KDF PBKDF2-HMAC-SHA-256, 600,000 iterations, random salt, random unique GCM IV.
- Password + exactly six-digit FIDUNIO PIN required together, unambiguous encoding.
- Firestore never contains plaintext password/PIN/private key/derived normal wrapping key/recovery RUK/master KEK.
- Exactly one Account E2EE Identity Manager owns create/unlock/recovery/re-wrap/publication; duplicate startup/auth callbacks join same serialized operation.
- Identity create-once; missing local state never authorizes replacement.
- Password/PIN changes re-wrap SAME private key; generate/verify candidate first, compare-and-update expected keyId/revision.
- Firebase Auth password update and Firestore wrapper update are not cross-service atomic; explicit recoverable staged flow required. Never destroy last valid recovery path.
- Transaction callbacks may retry; no crypto generation/UI side effects inside transaction callback.

ACCOUNT RECOVERY — AGREED
- Normal durable unlock: PASSWORD + EXISTING SIX-DIGIT FIDUNIO PIN together.
- Forgotten-password product requirement: legitimate recovery restores SAME E2EE identity/history.
- UX: verify registered recovery channel/email -> existing 6-digit PIN -> additional approved verification -> server recovery authorization -> same private key -> new password -> new normal wrapper -> history restored.
- No mandatory second device, QR, proprietary device ID or recovery-code requirement.
- Security questions supplemental only, never sole proof or cryptographic secret.
- Recovery uses small Firebase/Google serverless component + Secret Manager/KMS boundary; not normal messaging server.
- Recovery hardened with short-lived/single-use sessions, rate limits, enumeration resistance, notification, deterministic session review/invalidation and failure states.

OFFLINE MESSAGING — AGREED
- FIRESTORE = durable authoritative encrypted history.
- LOCAL CACHE = rebuildable offline/readable working copy.
- OUTBOX = one temporary owned local queue for encrypted pending sends.
- Offline read uses cache. Offline send remains Pending/Waiting, never falsely Sent.
- Reconnect automatically serially sends queued work, receives missed changes, reconciles cache and resumes live sync.
- Stable/idempotent message IDs prevent duplicates. Missing local DB = cache miss. UID-isolated cache prevents account leakage.
- Firestore SDK persistence may assist but cannot become competing Outbox owner. Do not rely on Firestore transactions while offline.
