IPAD SENT → READ DEFECT HISTORY
Original reproducible defect:
- iPad sends to iPhone.
- If iPhone conversation is already open, receipt can advance to Read on iPad.
- If iPhone leaves conversation, iPad sends another message, then iPhone re-enters and sees it, iPad can remain Sent.

0.8.1.10 FAILED:
- 2-second server polling caused constant refresh and broke sending. Rejected permanently; do not reintroduce polling.

0.8.1.11:
- Polling rollback restored normal messaging; receipt defect remained.

0.8.1.12 FAILED:
- Serialized async Firestore snapshot processing. Initial PASS was false positive; repeated testing reproduced defect.

0.8.1.13 FAILED:
- Removed ordinary two-pane force:true listener restarts at runtime. Defect remained. Therefore iPad forced two-pane listener replacement was not sufficient/root fix.

0.8.1.14 DIAGNOSTIC PARTIAL PASS:
- Added receipt metadata fast-path before peer-key refresh/decryption.
- User test: first message with iPhone conversation open changed to Read on iPad.
- After leaving iPhone conversation, second message sent from iPad and then viewed after re-entry remained Sent.
- This isolated the failure to recipient conversation re-entry/read advancement rather than a universal iPad rendering failure.

0.8.1.15 FAILED:
- Tried marking already-known incoming local rows Read from renderChat on entry.
- Same exact result: first/open-chat receipt works; message received while outside chat and viewed after re-entry remains Sent.
- Reason identified in source inspection: when narrow/mobile Back leaves chat, the active Firestore listener is not stopped. It can consume/cache the incoming message while route=messages, where read marking is intentionally suppressed. The local render-time attempt is not a reliable server-backed re-entry path.

0.8.1.16 CURRENT TEST:
- Restores established source listener behavior (removes failed v13 wide-layout runtime rewrite).
- Keeps v14 outgoing receipt metadata fast-path.
- Relies on the existing narrow/mobile conversation click force:true reattachment so re-entering the iPhone chat receives a fresh server-backed snapshot; existing subscription callback then marks incoming unread rows Read because route=chat and selected conversation match.
- No polling, Firestore Rules, E2EE, Outbox, or layout changes.
- Awaiting exact repeated test: open iPhone convo/read first message; leave convo; send second from iPad; re-enter iPhone convo; verify untouched iPad advances Sent → Read.
