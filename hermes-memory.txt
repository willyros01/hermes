RECOVERY SERVER — VALIDATED THREE-COMPONENT IMPLEMENTATION
- Recovery uses random 256-bit RUK; client recovery wrapper + PIN/server-master protected RUK. No plaintext password/PIN/RUK/private key/master secret in Firestore.

2026-09-06 — DISAPPEARING CONTENT READ-TIMER SEMANTICS
- User selected fixed-time-after-read semantics for both individual/direct and group disappearing messages.
- Direct message: the recipient account's first authoritative Read event starts that recipient's disappearance interval.
- Group message: each recipient account has its own independent first-Read timestamp and expiry window. One member reading does NOT start the timer for the other group members.
- The read/expiry authority must be server-backed and account-scoped; a device-local wall clock or UI-only read event is not sufficient authority.
- At a recipient's expiry, that recipient must no longer retain or project FIDUNIO-controlled local/cache/plaintext/grant copies of the content.
- Because a group message has one shared Firestore source ciphertext, the shared source record can be physically purged only after all still-authorized recipient expiry windows that apply to that source have elapsed (or a recipient is otherwise no longer entitled to the message). Final purge must also delete receipts, history-grant copies/references, attachment traces, local caches/Outbox remnants, and prevent stale-device resurrection.
- No per-message tombstone or retained expired:true source record is allowed after final purge.
- This decision resolves the timer-start ambiguity but does not mark disappearing content DONE. Exact metadata schema, authoritative timestamp write path, rules, purge owner, offline convergence and tests remain to be implemented.
