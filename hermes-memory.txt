ACCOUNT E2EE RECOVERY DECISIONS — SEPTEMBER 5, 2026
- Binding normal recovery requirement: PASSWORD + EXISTING 6-DIGIT FIDUNIO PIN MUST BE ENTERED TOGETHER to unlock/recover the durable account E2EE identity on a new/reinstalled context. Neither alone is sufficient.
- Never store plaintext password or plaintext PIN in Firestore. FIDUNIO app code must not persist the user's plaintext password in IndexedDB/localStorage. Firebase Authentication remains responsible for the authentication-password mechanism.
- Firestore may store public account E2EE material plus encrypted/wrapped private-key packages, salts/KDF/wrapping metadata and reviewed recovery material. Never plaintext private E2EE key.
- Password change: unlock existing identity with current valid credentials, change auth password, then re-wrap SAME E2EE identity using NEW PASSWORD + EXISTING PIN. Verify new wrapper before retiring old valid wrapper. History remains readable.
- PIN change: unlock existing identity, then re-wrap SAME E2EE identity using password + NEW PIN. History remains readable.
- Product requirement for forgotten-password recovery: once FIDUNIO's hardened recovery procedure legitimately establishes the account owner, that user regains the SAME E2EE identity and historical messages. Do not create a new messaging identity merely because Firebase password was reset.
- Agreed simple user recovery flow: Forgot Password -> verify registered recovery channel/email -> enter existing 6-digit PIN -> additional recovery verification -> choose new password -> recover SAME E2EE identity -> re-wrap with new password + PIN -> restore Firestore-authoritative history.
- DO NOT require another FIDUNIO device, QR transfer, proprietary device ID or device-to-device approval for normal recovery. User explicitly rejected another-device recovery as too difficult to implement/manage.
- Security questions, if retained, are SUPPLEMENTAL evidence only; not sole proof and not cryptographic recovery secret.
- Recovery hardened with random/short-lived/single-use challenges where applicable, rate limiting/throttling, account-enumeration protection, recovery notification, session invalidation/review, and deterministic enhanced verification/hold if adopted.
- Normal password+PIN wrapping cannot recover the old E2EE key when old password is forgotten, so a separate controlled recovery capability is required.

SERVER-SIDE RECOVERY AUTHORITY DECISION — SEPTEMBER 5, 2026
- User understands and AGREES to a small server-side FIDUNIO recovery component hosted in Firebase/Google infrastructure rather than placing the recovery secret in Firestore/client/GitHub.
- Intended direction: Cloud Functions for Firebase / Google Cloud serverless recovery function plus Google Secret Manager (or equivalently reviewed Google-managed secret facility) for protected recovery capability.
- This is NOT a general-purpose FIDUNIO server and does not put normal messaging through a server-side plaintext path. It is narrowly scoped to authorized forgotten-password recovery of the SAME durable account E2EE identity.
- Recovery secret/capability must not be exposed to browser JavaScript, Firestore, public GitHub source, logs or normal administrators. Access is scoped only to required recovery function(s).
- Recovery function does not store message plaintext, Firebase password or plaintext PIN and does not give administrators a plaintext-key bypass.
- Explicit tradeoff accepted: because legitimate forgotten-password recovery must preserve message history without second-device/recovery-code requirements, the FIDUNIO recovery authority becomes part of the security boundary for historical-key recovery.
- Exact recovery cryptographic construction, function authorization, Secret Manager/IAM boundary, audit, throttling and failure/rollback behavior must be specified before deployment.

OFFLINE MESSAGING DECISION — SEPTEMBER 5, 2026
- User reviewed and AGREES with simple offline model.
- FIRESTORE = durable authoritative/master encrypted conversation/message record.
- LOCAL CACHE = offline/readable working copy and rebuildable performance cache, not permanent authority.
- OUTBOX = temporary local queue for encrypted messages created while offline or awaiting authoritative cloud write.
- Offline read: display messages already present in local cache.
- Offline send: create encrypted pending message in Outbox and show deterministic Pending/Waiting state. Never claim Sent/Delivered before authoritative conditions are met.
- Reconnect: automatically send queued Outbox work to Firestore, receive authoritative changes missed while offline, reconcile/update local cache, then resume live synchronization. Ordinary user does not manually sync.
- Reconnect/startup must use one owned serialized path and idempotent message IDs so retries cannot create duplicate authoritative messages.
- Missing/deleted local database = cache miss, not lost account/history. Once authenticated, E2EE-ready and online, rebuild from Firestore.
- Local cached state must be UID-isolated to prevent account switching from exposing another account's local history.
- Firestore SDK persistence may assist but must not become a competing Outbox/state owner. FIDUNIO keeps explicit deterministic message status/Outbox ownership.
- Current Firebase documentation confirms Firestore web persistence can cache reads/writes and synchronize changes after reconnection; our explicit FIDUNIO Outbox/status layer remains necessary for deterministic messaging semantics and existing validated offline behavior.

DETERMINISTIC UI REQUIREMENT — SEPTEMBER 5, 2026
- User's explicit one-word requirement: DETERMINISTIC.
- All actions' results should be as expected. UI correctness must not depend on timing races, orientation changes, cache warming, repeated observers, asynchronous collision, or one module repairing another module after the fact.
- Goal is not synchronization of many writers; eliminate unnecessary writers and competing authorities.
- Authoritative application state first; DOM is projection.
- Every major UI region/screen has one structural owner and predefined DOM area.
- Broad MutationObserver repair, timeout settling, orientation rescue, cache-timing rescue, DOM rediscovery/re-parenting and location.reload synchronization prohibited as normal architecture.
- Responsive behavior is deterministic projection of same state. Preserve iPhone single-pane and iPad two-pane.
- Settings 0.9.5.1 is precedent: owned hosts, explicit lifecycle, no observer resurrection.
- UI architectural confidence ~60-65%; ~85-90% visual/user-facing design/functionality likely reusable. Do not wholesale redesign approved screens.
- Binding reference: `DETERMINISTIC-UI-LIFECYCLE.md`.

MAJOR ARCHITECTURE CORRECTION — SEPTEMBER 5, 2026
- Former rule `one account + one browser installation = one E2EE device identity` is SUPERSEDED.
- New binding invariant: ONE ACCOUNT = ONE DURABLE E2EE IDENTITY.
- Firebase Auth UID is durable identifier, not secret, and MUST NOT alone derive private key.
- Account E2EE key material cryptographically random and generated once.
- FIRESTORE authoritative for encrypted conversations/messages.
- LOCAL INDEXEDDB/STORAGE rebuildable cache; Outbox temporary offline queue.
- PWA reinstall, Safari/PWA context change, cache deletion, replacement device must not by themselves destroy history.
- Device ID informational only. DO NOT use for E2EE routing/key ownership/message ownership/history/decryptability/normal delivery.
- Existing per-device E2EE envelope/fan-out is legacy migration material, not target.
- Future FCM tokens associated with UID; separate from E2EE.
- Old-architecture messaging baseline testing remains paused until new durable account E2EE design implemented in bounded steps.
