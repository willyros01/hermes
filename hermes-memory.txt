ACCOUNT E2EE RECOVERY DECISIONS — SEPTEMBER 5, 2026
- Binding normal recovery requirement: PASSWORD + EXISTING 6-DIGIT FIDUNIO PIN MUST BE ENTERED TOGETHER to unlock/recover the durable account E2EE identity on a new/reinstalled context. Neither alone is sufficient.
- Never store plaintext password or plaintext PIN in Firestore. FIDUNIO app code must not persist the user's plaintext password in IndexedDB/localStorage. Firebase Authentication remains responsible for the authentication-password mechanism.
- Firestore may store the public account E2EE material plus an encrypted/wrapped private-key package, salts/KDF/wrapping metadata, and a separately designed recovery-wrapped representation or equivalent recovery material. Never plaintext private E2EE key.
- Password change: unlock existing identity with current valid credentials, change auth password, then re-wrap the SAME E2EE identity using NEW PASSWORD + EXISTING PIN. Verify new wrapper before retiring old valid wrapper. History must remain readable.
- PIN change: unlock existing identity, then re-wrap SAME E2EE identity using password + NEW PIN. History remains readable.
- Product requirement for forgotten-password recovery: once FIDUNIO's hardened recovery procedure legitimately establishes the account owner, that user SHOULD regain the SAME E2EE identity and historical messages. Do not silently create a new messaging identity merely because the Firebase password was reset.
- Agreed simple user recovery flow: Forgot Password -> verify registered recovery channel/email -> enter existing 6-digit PIN -> additional recovery verification -> choose new password -> recover SAME E2EE identity -> re-wrap with new password + PIN -> restore Firestore-authoritative history.
- DO NOT require another FIDUNIO device, QR transfer, proprietary device ID, or device-to-device approval for normal account recovery. User explicitly rejected another-device recovery as too difficult to implement/manage.
- Security questions, if retained, are SUPPLEMENTAL evidence only. They must not be the sole proof or the cryptographic secret that releases message history. Current NIST guidance does not consider traditional knowledge-based questions a strong standalone recovery authenticator.
- Recovery must be hardened: random/short-lived/single-use challenges where applicable; rate limiting/throttling; protection against account enumeration; security notification after successful recovery; session invalidation/review after high-risk recovery; deterministic enhanced verification/hold for suspicious recovery if adopted.
- Normal password+PIN wrapping cannot mathematically recover an old E2EE key when the old password is forgotten. Therefore a separate explicit recovery capability/recovery wrapper (or equivalent reviewed construction) is required. Identity verification must connect to key recovery through a controlled cryptographic mechanism.
- No administrator gets a plaintext-key bypass. No plaintext E2EE private key in Firestore.
- Exact KDF, wrapping algorithm, Firestore schema, recovery-wrapper authority, throttling policy, password/PIN re-wrap transaction, rollback behavior, and Firestore rules MUST be specified/reviewed before application implementation.
- Binding detailed reference: `ACCOUNT-E2EE-FIRESTORE-AUTHORITY.md`.

DETERMINISTIC UI REQUIREMENT — SEPTEMBER 5, 2026
- User's explicit one-word requirement: DETERMINISTIC.
- All actions' results should be as expected. UI correctness must not depend on timing races, orientation changes, cache warming, repeated observers, asynchronous collision, or one module repairing another module after the fact.
- The goal is NOT increasingly masterful synchronization of many writers. Eliminate unnecessary writers and competing authorities.
- Authoritative application state comes first; DOM is a projection.
- Every major UI region/screen has one structural owner and predefined DOM area.
- Broad MutationObserver repair, timeout settling, orientation rescue, cache-timing rescue, DOM rediscovery/re-parenting, and location.reload synchronization are prohibited as normal architecture.
- Responsive behavior is deterministic projection of same state. Preserve iPhone single-pane and iPad two-pane.
- Settings 0.9.5.1 is the precedent: owned hosts, explicit lifecycle, no observer resurrection.
- UI architectural confidence ~60-65%; ~85-90% visual/user-facing design/functionality likely reusable. Do not wholesale redesign approved screens.
- Binding reference: `DETERMINISTIC-UI-LIFECYCLE.md`.

MAJOR ARCHITECTURE CORRECTION — SEPTEMBER 5, 2026
- Former rule `one account + one browser installation = one E2EE device identity` is SUPERSEDED.
- New binding invariant: ONE ACCOUNT = ONE DURABLE E2EE IDENTITY.
- Firebase Auth UID is durable identifier, not secret, and MUST NOT alone derive private key.
- Account E2EE key material is cryptographically random and generated once.
- FIRESTORE IS AUTHORITATIVE for encrypted conversations/messages.
- LOCAL INDEXEDDB/STORAGE IS REBUILDABLE CACHE; Outbox temporary offline queue.
- PWA reinstall, Safari/PWA context change, cache deletion, replacement device must not by themselves destroy history.
- Device ID may be collected as informational variable only. DO NOT use for E2EE routing/key ownership/message ownership/history/decryptability/normal delivery.
- Existing per-device E2EE envelope/fan-out is legacy migration material, not target architecture.
- Future FCM tokens associated with UID; separate from E2EE.
- Current old-architecture messaging baseline testing remains paused until new durable account E2EE design is implemented in bounded steps.
