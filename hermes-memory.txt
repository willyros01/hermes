PERMANENT E2EE DEVICE-IDENTITY INVARIANT — SEPTEMBER 4, 2026
- Mandatory reference: `E2EE-IDENTITY-LIFECYCLE.md`.
- One authenticated FIDUNIO account on one browser installation has one stable E2EE device ID + ECDH keypair.
- App updates, refreshes, logout/login, reconnects, service-worker updates, and normal account switching MUST NOT rotate or regenerate that identity.
- A fresh identity is created only when BOTH identity and keypair are absent, or after an explicit user-approved reset/revocation. Partial identity state must fail safely; never silently manufacture a replacement half.
- Concrete race found in 0.9.5.6: `initializeFirebaseLayer()` can call `publishMyE2EEKey()` twice during startup, while keypair/device creation previously had no shared mutex. Concurrent first-start calls could therefore create competing keys/device IDs.
- 0.9.5.7 serializes keypair+device-ID creation as one pair and serializes cloud publication. Duplicate startup callers join the same promise.
- 0.9.5.5 automatic quarantine identity restoration is disabled during ordinary startup because it could replace a valid current identity. Recovery/reset must be explicit.
- Historical vault/message data is test data and need not be recovered. After 0.9.5.7 identity stability passes, perform one deliberate cleanup of stale cloud device registrations and obsolete local vault/history/Outbox test data, then establish a fresh baseline.

CURRENT CRITICAL ARCHITECTURAL DISCOVERY — SEPTEMBER 4, 2026
- The repository currently has a hidden dual-code runtime.
- Raw `app.js` still contains prototype-era runtime state/UI, including Maria Santos, John Cruz, Family Group, sample contacts, local numeric IDs, and prototype group assumptions.
- `service-worker.js` is not merely caching the application: it rewrites `app.js` source at runtime and injects later production behavior, including important receipt, E2EE/per-device fan-out, group, and related functionality.
- Therefore raw repository `app.js` and the application actually validated under service-worker control are not necessarily the same program.
- This explains why prototype UI/data and apparently removed behavior can reappear on cold/uncontrolled loads and why direct cleanup of raw `app.js` is dangerous.
- Do NOT simply delete prototype arrays or service-worker replacements. Some string-replacement anchors currently carry validated production behavior.

- Profile, User Administration, and Invitations were late bolt-ons outside the authoritative Settings render lifecycle.
- Old broad MutationObservers recreated/reparented them after `app.js` rebuilt Settings.
- Correct rule: authoritative screen lifecycle creates owned hosts and explicitly mounts/remounts feature owners; no observer rediscovery and no cross-owner re-parenting.
- Settings 0.9.5.1 currently demonstrates the desired ownership direction and must be protected during runtime consolidation.

PIN / LOCAL SECURITY
- `app.js state.unlocked` remains the single authoritative local LOCKED/UNLOCKED state.
- `local-security.js` is helper-only and must not create a competing lock state/UI.
- PIN config is installation-local in IndexedDB; raw PIN is never stored; PBKDF2-SHA256 verifier, random salt, 210000 iterations; 4-12 digits.
- WebAuthn platform authenticator with PIN fallback.
- Firebase authentication and local unlock remain separate.
- Lock Now and inactivity use the same lock authority.
- Known open bug: Remove Local PIN does not work. Change PIN, Lock Now, timeout and existing PIN flows are working. Fix later as a focused local-security defect; do not redesign the working architecture.
