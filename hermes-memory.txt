STABLE TRANSPORT / OFFLINE BASELINE
==================================================

0.6.5 — STABLE TRANSPORT/OFFLINE BASELINE

Root cause fixed:
- Offline Firestore onSnapshot could emit empty/incomplete cached snapshots with metadata.fromCache === true.
- Earlier builds overwrote restored local history with [].

0.6.5 behavior:
- Cache snapshots merge non-destructively and never erase local rows.
- Server-backed snapshots authoritative except local pending outbound.
- Local-first startup:
  loadPersistedState()
  → loadCloudHistory()
  → restoreOutboxIntoState()
  → hydrated=true
  → render()
  → initializeFirebaseLayer()
  → flush if online.
- Read receipts only server-backed.
- Firebase data never service-worker cached.

User test PASS:
- Repeated offline/online cycles retained all messages.
- Queued message automatically sent when communications returned.

Treat 0.6.5 local-first persistence as stable and do not change without a specific defect.

==================================================
E2EE HISTORY
==================================================

0.7.0 — E2EE FOUNDATION

Direct-message E2EE:
- Each installation generates Web Crypto ECDH P-256 key pair.
- Private key non-exportable.
- Stored in IndexedDB meta key e2ee-device-keypair-v1.
- Public JWK published on user profile as e2eePublicJwk.
- ECDH shared secret.
- HKDF-SHA-256:
  salt = FIDUNIO-E2EE-v1
  info = conversation ID.
- AES-256-GCM with fresh 12-byte IV.
- Conversation ID used as AAD.
- Firestore encrypted rows use:
  e2ee:1
  ciphertext
  iv
  text:""
  sender metadata/time/state.
- Recipient decrypts locally.
- Outbox plaintext exists only inside existing locally AES-GCM encrypted IndexedDB record before cloud encryption.
- Missing/decrypt-failure UI:
  [Encrypted message — key unavailable]
- Legacy plaintext rows remain readable.
- Auth restoration republishes own public key.

Known limitations at this stage:
- One active installation/device key per account assumption.
- No multi-device fan-out.
- Clearing site data/reinstall creates a new key.
- No safety-number verification.
- No key-change approval.
- No forward secrecy / Double Ratchet.
- No group E2EE.
- Metadata visible.
- Old cloud messages remain plaintext.

==================================================
SECURITY MODEL / ROADMAP
==================================================

Current layered model:
Authentication
→ App Check later
→ Firestore Security Rules
→ E2EE

Important:
- Firebase Web API key/config is public by design.
- Knowing client JS/config does not let an attacker modify Firestore Security Rules.
- Rules are server-side and apply to hostile custom clients.
- Main risks include overly broad rules, stolen admin/IAM credentials, leaked service-account keys, and quota/resource abuse.
- Never commit service-account private keys.

GitHub secret-scanning alert:
- Google API Key detected in firebase-config.js.
- Likely expected Firebase Web API key detection.
- Low-priority hardening task for later:
  verify it is only the Firebase web key
  check Google Cloud API restrictions
  resolve GitHub alert appropriately.
- Do not rotate/delete solely because of the alert.
