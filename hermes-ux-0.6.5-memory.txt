0.6.5 CONCRETE ROOT-CAUSE FIX
Firestore onSnapshot can emit a cached/offline snapshot during cold start.
Earlier FIDUNIO code replaced `state.messages[conversationId]` with the Firestore
snapshot rows. An empty/incomplete cache snapshot could therefore erase locally
restored messages in memory, after which the empty result was persisted.
When a server snapshot arrived after reconnect, messages reappeared.

0.6.5 changes:
- firebase.js passes snapshot metadata: fromCache and hasPendingWrites.
- fromCache snapshots merge into local durable history and NEVER remove local rows.
- server-backed snapshots are authoritative for Firestore rows.
- queued/sending/failed local messages remain preserved until confirmed remotely.
- read receipts are not sent from cache-only snapshots.
- startup order is explicitly:
  local encrypted app state
  -> dedicated encrypted cloud history
  -> encrypted Outbox reconstruction
  -> render
  -> Firebase synchronization
- service worker changed to Scorecard-style architecture:
  own files network-first/cache fallback;
  gstatic Firebase SDK cache-first/background refresh;
  googleapis/firebaseio transport never cached.
- Firebase SDK top-level modules are opportunistically pre-cached at worker install.
- existing Outbox and live-listener safeguards remain.
